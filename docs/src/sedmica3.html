Okvir nastavne jedinice

Ciljevi i način rada

U drugoj sedmici su mašine napravljene iz koda: Terraform ih je kreirao, cloud-init personalizovao, a Packer pripremio sliku. Ostalo je pitanje šta se događa unutar mašine nakon toga: paketi, konfiguracijske datoteke, servisi, tajne. Taj dio rješava upravljanje konfiguracijom, predstavljeno kroz Ansible. Druga polovina sedmice prenosi isti način razmišljanja na kontejnere: aplikacija i okruženje se opisuju datotekama (Dockerfile, compose.yaml, Kubernetes manifesti), a ne naredbama upisanim ručno.

Nakon nastavne jedinice student je u stanju:

  • objasniti razliku između provisioninga (Terraform) i upravljanja konfiguracijom (Ansible) i povezati ih u jedan tok,
  • napisati inventory, playbook i šablon (Jinja2) te provjeriti idempotentnost izvršavanja,
  • organizovati kod u rolu i zaštititi osjetljive vrijednosti Ansible Vaultom,
  • generisati Ansible inventory iz Terraform izlaza,
  • napisati Dockerfile i Compose datoteku za aplikaciju s bazom i povezati slojeve slike s prvom sedmicom,
  • pročitati osnovni Kubernetes manifest i objasniti razliku između Terraform i Kubernetes pristupa usklađivanju stanja.

Okruženje i pokretanje

Alati za ovu sedmicu (Ansible, Docker, kubectl, kind) instalira skripta 00-setup.sh (opisana u bilješkama za sedmicu 2). Ako je već pokrenuta, dovoljno je ažurirati repozitorij i pokretati primjere redom:

Rad bez troškova: pregled umjesto izvršavanjaSvaki alat ima način da pokaže šta bi uradio bez izmjene sistema: terraform plan, ansible-playbook --check --diff, docker compose config i kubectl apply --dry-run. Osnovni cilj svakog primjera koristi baš to, a stvarno izvršavanje je opcionalno (-apply, -up). Svi ciljevi su idempotentni: mogu se ponavljati. Napomena: --check ne zna šta bi se desilo nakon zadatka koji još nije izvršen, pa dio zadataka može prijaviti grešku koju prava izvedba ne bi imala.
VažnoRepozitorij mora biti u Linux fajl sistemu (~/), ne u /mnt/c/...: Ansible ignoriše ansible.cfg u direktoriju u koji svi mogu pisati, pa Vault i uloge ne bi radili.
1 · Pojam i pozadina

Od provisioninga do upravljanja konfiguracijom

Terraform odgovara na pitanje koji resursi postoje (mašine, mreže, diskovi), ali se ne bavi onim što je unutar mašine. cloud-init to rješava samo pri prvom pokretanju, a promjene u radu (nova konfiguracija, novi korisnik, zakrpa) ostaju bez vlasnika. Za taj dio služi alat za upravljanje konfiguracijom.

Pozadina: AnsibleAnsible je nastao 2012. (Michael DeHaan), a od 2015. ga razvija Red Hat. Za razliku od starijih alata (Puppet, Chef) nema agenta: ne instalira se ništa na upravljane mašine. Kontrolni čvor se spaja preko SSH-a, kopira male Python module, izvršava ih i briše. Zato mašini trebaju samo SSH i Python, a ono što cloud-init pripremi (korisnik i SSH ključ) je upravo ono što Ansible traži. Pisan je u YAML-u, što ga čini čitljivim.
  • Bez agenta. SSH + Python, bez posebnog softvera na mašinama.
  • Push model. Kontrolni čvor šalje konfiguraciju kad se izda naredba.
  • Deklarativni moduli. Zadatak ne kaže "izvrši apt install nginx", nego "paket nginx treba biti prisutan". Modul provjeri stanje i mijenja samo ako treba: idempotentnost iz druge sedmice.
PojamZnačenje
InventorySpisak mašina podijeljenih u grupe ([web], [db]) uz pripadajuće varijable.
ModulJedinica posla (apt, service, template, user, file...). Većina je idempotentna.
TaskJedan poziv modula s parametrima.
Play / playbookPlay veže grupu mašina (hosts) s listom zadataka. Playbook je YAML datoteka s jednim ili više playeva.
HandlerZadatak koji se izvršava samo ako ga je neki zadatak "obavijestio" (notify) da je nešto promijenio, npr. reload servisa nakon izmjene konfiguracije.
RolePakovanje zadataka, šablona, varijabli i handlera u višekratno upotrebljivu cjelinu.
FactPodatak koji Ansible prikupi o mašini (OS, adrese, memorija). Koristi se u uslovima i šablonima.
VaultŠifrovanje osjetljivih datoteka i vrijednosti u repozitoriju.
Granica idempotentnostiModuli command i shell ne znaju ništa o stanju, pa su uvijek changed. Koriste se tek kad ne postoji odgovarajući modul, uz creates: ili changed_when: koji im vraćaju provjeru stanja.
2 · Primjer 1 · s3/p1

Inventory, playbook i šablon

Pozadina primjeraPostavlja se nginx s vlastitom početnom stranicom. Cilj je lokalna mašina (ansible_connection=local), pa Ansible ne koristi SSH nego izvršava module direktno. Isti playbook radi na laptopu i na VM-u iz druge sedmice; mijenja se samo inventory. Početna stranica je šablon (Jinja2): {{ varijabla }} se zamjenjuje vrijednošću, a facts daju podatke o mašini.
yamlIsječak 1 · s3/p1/site.yml
- name: Web server
  hosts: web
  become: true
  vars:
    naslov: "Računarstvo u oblaku, sedmica 3"
  tasks:
    - name: nginx je instaliran
      ansible.builtin.apt: { name: nginx, state: present, update_cache: true, cache_valid_time: 3600 }

    - name: početna stranica iz šablona
      ansible.builtin.template:
        src: index.html.j2
        dest: /var/www/html/index.html
        mode: "0644"
      notify: reload nginx

    - name: nginx radi i uključen je pri pokretanju
      ansible.builtin.service: { name: nginx, state: started, enabled: true }

  handlers:
    - name: reload nginx
      ansible.builtin.service: { name: nginx, state: reloaded }
jinja2Isječak 2 · s3/p1/templates/index.html.j2
<h1>{{ naslov }}</h1>
<p>Host: {{ ansible_facts['hostname'] }},
   OS: {{ ansible_facts['distribution'] }} {{ ansible_facts['distribution_version'] }}</p>

Najvažniji red je changed=0 u drugom izvršavanju. Isto se može provjeriti i drift konfiguracije: ručno izmijeniti /var/www/html/index.html i ponovo pokrenuti. Zadatak template će prijaviti changed, vratiti sadržaj i pozvati handler. Handler se izvršava samo kad je prethodni zadatak nešto promijenio, zato se reload ne radi pri svakom pokretanju. Pri provjeri --check --diff prikazuje se razlika (diff) datoteke koja bi se promijenila.

Inventory, grupe i varijable

Inventory se može pisati u INI ili YAML obliku. Varijable se ne drže u njemu nego u group_vars/<grupa>/ i host_vars/<host>/, pa se podaci i spisak mašina održavaju odvojeno. Pregled grupa: ansible-inventory -i inventory.yml --graph.

yamlIsječak 4 · inventory.yml (ilustracija)
all:

        web1: { ansible_host: 192.168.122.57, ansible_user: student }
        web2: { ansible_host: 192.168.122.58, ansible_user: student }
    db:
      hosts:
        db1:  { ansible_host: 192.168.122.60, ansible_user: student }

3 · Primjer 2 · s3/p2

Role i Ansible Vault

Pozadina primjeraKad playbook naraste, zadaci i datoteke se pakuju u rolu s fiksnom strukturom direktorija, pa je lako ponovo upotrijebiti i dijeliti (javni skup rola je Ansible Galaxy). Primjer pravi rolu webserver i dodaje tajnu (lozinku baze) koja se šifruje Vaultom, tako da u Gitu nikad ne završi u čistom tekstu. Vault šifruje datoteku algoritmom AES256 i lozinkom koja se čuva izvan repozitorija.
Direktorij roleSadržaj
tasks/main.ymlZadaci role.
handlers/main.ymlHandleri.
templates/, files/Šabloni (Jinja2) i statične datoteke.
defaults/main.ymlPodrazumijevane vrijednosti varijabli (najniži prioritet, lako se nadjačaju).
yamlIsječak 5 · s3/p2/roles/webserver/tasks/main.yml
- name: nginx je instaliran
  ansible.builtin.apt: { name: nginx, state: present, cache_valid_time: 3600 }

- name: početna stranica
  ansible.builtin.template: { src: index.html.j2, dest: /var/www/html/index.html, mode: "0644" }
  notify: reload nginx

- name: direktorij za konfiguraciju aplikacije
  ansible.builtin.file: { path: /etc/ruo, state: directory, mode: "0750" }

- name: tajna aplikacije (samo root može čitati)
  ansible.builtin.template: { src: app.env.j2, dest: /etc/ruo/app.env, owner: root, mode: "0600" }
  no_log: true                 # vrijednost se ne ispisuje u izlazu

- name: nginx radi
  ansible.builtin.service: { name: nginx, state: started, enabled: true }

Prema dogovoru, obična varijabla u group_vars/web/vars.yml samo upućuje na šifrovanu varijablu s prefiksom vault_. Tako se u kodu vidi odakle vrijednost dolazi, a pretraga ostaje moguća.

# group_vars/web/vault.yml (šifrovano, NIJE u Gitu u ovom labu)

4 · Terraform + Ansible · Primjer 3 · s3/p3

Dva alata, jedan tok

Pozadina primjeraTerraform stvara mašine i na izlazu daje njihove adrese. Ansible čita te adrese i konfiguriše mašine. Kritična tačka je prenos podataka: Ansible mora znati koje mašine su napravljene. Spona je inventory, a u ovom primjeru ga Terraform generiše kao običan resurs (local_file). cloud-init se svodi na bootstrap (korisnik i SSH ključ, dovoljno da se Ansible prijavi), a sve ostalo preuzima rola iz primjera 2.
PristupKakoOcjena
Terraform generiše inventorylocal_file s inventoryjem iz izlaza VM-a. Ansible se pokreće zasebno.Jednostavno i jasno. Koristi se ovdje.
local-exec provisionerTerraform sam poziva ansible-playbook.Dokumentacija ga svrstava u "krajnju mjeru": greška u Ansible-u ruši apply, a plan ne pokazuje šta će Ansible raditi.
Dinamički inventoryAnsible plugin sam upita API oblaka.Najelegantnije u oblaku, više podešavanja.

5 · Kontejneri kao kod

Dockerfile i slojevi

PozadinaIz prve sedmice: kontejner je proces s izolovanim pogledom na resurse, a slika je OCI paket slojeva fajl sistema. Docker je (2013) učinio taj model dostupnim jednostavnom komandom, a ispod njega rade containerd i runc. Dockerfile je recept za izgradnju slike. Svaka instrukcija pravi novi sloj (overlayfs iz prve sedmice), a Docker slojeve kešira: ako se instrukcija i sve prije nje nisu promijenile, koristi se postojeći sloj.
InstrukcijaZnačenje
FROMOsnovna slika. Navodi se konkretna verzija (python:3.12-slim), ne latest.
WORKDIR, COPYRadni direktorij i kopiranje datoteka u sliku.
RUNNaredba pri izgradnji (instalacija zavisnosti). Stvara sloj.
ENV, EXPOSEVarijable okruženja i dokumentovanje porta (ne objavljuje ga).
USERKorisnik pod kojim radi proces (ne root).
HEALTHCHECKKako Docker provjerava da li je proces zdrav.
CMD / ENTRYPOINTŠta se pokreće. ENTRYPOINT je fiksni program, a CMD njegovi podrazumijevani argumenti.

Dobra praksa: stalno promjenjivo ide pri dnu (da keš ostane važeći), .dockerignore izbacuje suvišne datoteke, proces ne radi kao root, a tajne se nikad ne upisuju u sliku jer ostaju u slojevima čak i kad se kasnije obrišu. Multi-stage izgradnja koristi jednu sliku za izgradnju, a drugu, manju, za izvršavanje.

6 · Primjer 4 · s3/p4

Aplikacija s bazom u Docker Composeu

Pozadina primjeraJednostavna aplikacija (Flask) broji posjete i čuva brojač u Redisu (baza u memoriji). Dockerfile opisuje aplikaciju, a Docker Compose (compose.yaml) deklarativno opisuje cijeli sistem na jednom računaru: koje usluge postoje, kako su povezane, koje podatke čuvaju i kada su spremne. Za razliku od prethodnih primjera, ovdje se sve izvršava lokalno i besplatno, pa osnovni cilj radi stvarni up.
dockerfileIsječak 11 · s3/p4/app/Dockerfile
# --- faza 1: instalacija zavisnosti (zasebna zbog keša slojeva) ---
FROM python:3.12-slim AS build
WORKDIR /w
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# --- faza 2: finalna slika ---
FROM python:3.12-slim
RUN useradd --system --uid 10001 app
WORKDIR /app
COPY --from=build /install /usr/local
COPY app.py .
USER app
EXPOSE 8000
HEALTHCHECK --interval=10s --timeout=3s --retries=3 \
  CMD python -c "import urllib.request as u; u.urlopen('http://127.0.0.1:8000/health', timeout=2)"
CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]

Zavisnosti se kopiraju i instaliraju prije koda aplikacije: dok se requirements.txt ne promijeni, svaka izmjena u app.py koristi keširane slojeve. Multi-stage ovdje služi uglavnom kao ilustracija; velika korist se vidi kod kompajliranih jezika (Go, Java, C), gdje se kompajler ostavlja u prvoj fazi.

yamlIsječak 12 · s3/p4/compose.yaml
services:
  web:
    build: ./app
    image: ruo/brojac:1.0
    ports: ["8080:8000"]
    environment: { REDIS_HOST: redis }
    depends_on:
      redis: { condition: service_healthy }   # web čeka dok Redis ne postane zdrav
    restart: unless-stopped
    networks: [backend]

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes: [redisdata:/data]                # podaci prežive brisanje kontejnera
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5
    networks: [backend]                       # port NIJE objavljen: dostupan samo web usluzi

volumes:
  redisdata:
networks:
  backend:

Compose se ponaša kao Terraform: poredi željeno i stvarno stanje, a pri ponovnom pokretanju obnavlja samo usluge čija se definicija promijenila (up -d bez izmjena ne radi ništa). 7 · Kubernetes · Primjer 5 · s3/p5

Uvod u manifeste

PozadinaCompose upravlja kontejnerima na jednom računaru. Kubernetes (Google, 2014, nasljednik internog sistema Borg; danas ga održava CNCF) upravlja njima na skupu računara (klaster): raspoređuje ih, nadzire, zamjenjuje pokvarene i skalira. Sistem je deklarativan: manifest (YAML) opisuje željeno stanje, a kontroleri unutar klastera neprekidno usklađuju stvarno stanje s njim. Lokalni klaster pravi kind ("Kubernetes in Docker": čvorovi klastera su Docker kontejneri), pa nije potreban oblak.
ObjektUloga
PodNajmanja jedinica: jedan ili više kontejnera koji dijele mrežu i volumene. Prolazan je.
DeploymentOdržava traženi broj kopija Poda (replicas) i vodi izmjene verzija (rolling update).
ServiceStabilna adresa i balansiranje prema Podovima odabranim po oznakama (labels).
ConfigMap / SecretKonfiguracija i osjetljive vrijednosti odvojene od slike. Secret je samo base64 kodiran, nije šifrovan.
NamespaceLogička podjela klastera.
Poređenje s TerraformomTerraform usklađuje stanje na zahtjev (kad se pokrene apply), a drift se otkriva samo tada. Kubernetes ga usklađuje neprekidno: ako se Pod ugasi, kontroler ga odmah ponovo napravi. Stanje koje Terraform čuva u tfstate, Kubernetes drži u svojoj bazi (etcd). Zajednička ideja: željeno stanje zapisano kao kod, sistem ga provodi.
yamlIsječak 14 · s3/p5/web.yaml (skraćeno)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: nginx
          image: nginx:1.27-alpine
          ports: [{ containerPort: 80 }]
          readinessProbe:
            httpGet: { path: /, port: 80 }
          resources:
            requests: { cpu: 50m, memory: 32Mi }
            limits:   { memory: 64Mi }      # postaje cgroup memory.max (sedmica 1)
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector: { app: web }

Zadaci za samostalni rad

  1. U s3/p1 dodati zadatak koji kreira korisnika deploy i pokrenuti playbook dva puta; objasniti zašto je drugi put changed=0.
  2. U roli iz s3/p2 nadjačati naslov u group_vars/web/vars.yml i dodati novu tajnu pomoću ansible-vault encrypt_string.
  3. U s3/p3 napraviti dvije mašine (for_each) tako da inventory ima obje. Predati izlaz terraform plan.
  4. U Compose datoteku dodati treću uslugu (nginx kao obrnuti proxy ispred web) i ukloniti objavljeni port s web.
  5. Isti sistem iz primjera 4 napisati kao Kubernetes manifest (Deployment + Service za web i redis); sliku učitati u kind pomoću kind load docker-image.
